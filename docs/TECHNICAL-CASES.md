## 정산 응답 유실과 중복 전표

- **문제와 영향** — 서버가 실비 정산을 커밋한 직후 응답이 끊기면 화면에는 실패로 보입니다. 재시도 때 약정을 두 번 해제하거나 같은 경비를 다시 집행하면 장부가 어긋납니다.
- **재현과 원인** — 200,000원을 약정하고 실비 225,000원의 정산 요청을 보냅니다. Playwright에서 실제 서버 응답이 200인 것을 확인한 뒤 브라우저에 전달할 응답만 끊습니다. 그 상태에서 원장을 조회하면 첫 정산은 이미 기록돼 있습니다. 브라우저가 관측한 전송 실패만으로는 서버의 커밋 여부를 알 수 없습니다.
- **선택과 트레이드오프** — 화면에서 버튼을 잠그면 연속 클릭은 줄일 수 있지만 새 세션이나 통신 장애 뒤의 재요청은 막기 어렵습니다. 서버에서 부서 예산 행과 신청 행을 잠근 다음, 요청 차수가 맞고 이미 정산됐으면 기존 결과를 유지합니다. 같은 부서의 회계 처리가 잠금 해제까지 대기하지만 예산 잔액, 상태, 전표와 송신 대기 행을 한 트랜잭션에서 관리할 수 있습니다.
- **구현과 검증** — 같은 차수의 최초 확정만 약정 −200,000원과 집행 +180,000원을 기록합니다. 공개 데모에서 재요청도 200을 반환했고 재전송 전후 전표는 승인·정산 두 건으로 같았습니다. 정산 전표는 1건, 누적 집행액은 180,000원, 가용액은 820,000원이었습니다. 원래 차수와 다른 요청은 차수 검사에서 거절됩니다. 부하에 따른 잠금 대기는 별도의 동시 승인 실험에서 측정했습니다.

## Oracle 결재함의 깊은 페이지

- **문제와 영향** — 최신순 결재함에서 뒤쪽 페이지를 열수록 OFFSET으로 건너뛸 행이 늘어 같은 수의 신청을 가져오는 데 더 많은 DB 읽기가 필요했습니다.
- **재현과 원인** — Oracle에 합성 부서 100개와 신청 100만 건을 생성했습니다. 50번째 부서의 최신 9,000행 다음부터 같은 열과 순서의 51행을 비교했습니다. OFFSET 계획은 앞의 행을 지나간 뒤 필요한 행을 내보냈고, 키셋 계획은 부서와 마지막 접수 순번을 조건으로 해당 위치에서 읽기 시작했습니다.
- **선택과 트레이드오프** — OFFSET은 페이지 번호로 이동하기 쉽지만 깊어질수록 버리는 행이 늘어납니다. 이 결재함은 최신순으로 계속 읽는 업무이므로 이미 읽은 마지막 행의 순번을 커서로 사용했습니다. 순서가 안정적이어야 하고 정렬·필터를 바꾸면 경계도 다시 잡아야 합니다. 임의 페이지로 바로 이동하려면 별도 탐색 방법이 필요합니다.
- **구현과 검증** — MyBatis 매퍼에서 부서, 상태 조건, 커서를 바인딩하고 51행을 가져옵니다. 50행을 표시하고 여분 한 행으로 다음 페이지 유무를 판정합니다. 같은 51행에서 논리 읽기는 **307회 → 13회**였습니다. 예열한 단일 세션에서 각 SQL을 40회 인출한 Oracle 서버 p95는 **6.608ms → 0.137ms**였습니다. 브라우저 표시 시간과 동시 쓰기 비용은 이 측정의 범위 밖입니다.

## React 신청함의 첫 렌더링

- **문제와 영향** — 직원 화면을 처음 열어 신청하면 접수 완료 문구가 떠도 React 신청함이 비어 있을 수 있었습니다. 다시 제출해야 하는지 판단하기 어려웠습니다.
- **재현과 원인** — Playwright에서 `employee.js`의 첫 응답을 보류한 상태로 JSP 신청 접수를 완료하고 React 모듈을 계속 로드합니다. React의 첫 상태 읽기와 이벤트 구독 등록 사이에 변경이 들어오면 예전 목록이 남을 수 있었습니다. 같은 세션에서 화면을 다시 열었을 때는 결재 대기 신청 한 건이 있었습니다.
- **선택과 트레이드오프** — React가 준비될 때 목록 API를 다시 호출하는 방식은 구현이 단순하고 서버 최신값을 받을 수 있지만 동일 조회가 한 번 더 일어납니다. 두 화면이 쓰는 외부 상태의 최신 스냅샷이 있으므로 `useSyncExternalStore`로 직접 읽고 변경을 구독하도록 했습니다. 조회를 덧붙이지 않는 대신 두 화면이 상태 갱신과 이벤트 통지 규약을 지켜야 합니다.
- **구현과 검증** — `EmployeeInbox`가 공유 스냅샷과 구독 함수를 사용합니다. 번들을 늦게 풀어주는 회귀 시험에서 먼저 접수한 신청 한 건과 결재 대기 상태를 확인했습니다. 로컬 Chrome에서 지연 로딩과 기기별 보완 흐름을 두 차례씩 확인했고 공개 배포의 Chrome 기록에도 이 회귀 시험이 있습니다. 이것은 누락 방지 결과이며 표시 시간 단축은 이 사례에서 측정하지 않았습니다.

## 동시 승인과 가용 예산

가용액 100,000원에서 별도 신청 두 건을 각각 80,000원씩 승인하면, 신청 행만 잠가서는 같은 잔액을 두 처리에서 읽을 수 있습니다. 공통 자원인 부서 예산 행을 먼저 잠그고 잔액 검사와 전표 기록을 같은 트랜잭션에서 처리했습니다. 다른 부서는 각자의 예산 행을 사용하지만 같은 부서의 승인은 서로 기다립니다. 실제 Oracle에서 동시 승인 22쌍(예열 2쌍 포함) 전부 **200·422 각 한 건, 약정 전표 1건, 잔액 20,000원**을 확인했습니다. 별도의 JDBC 실험에서 동일 부서 잠금 조회 p95는 101.134ms, 다른 부서는 0.660ms였습니다. 첫 세션이 100ms 후 잠금을 해제한 조건의 수치입니다. ## 프론트엔드 정적 자산 캐시

같은 결재함을 다시 열 때 자체 CSS와 JavaScript가 재전송됐습니다. 고정 주소의 짧은 캐시는 변경 전달이 단순하지만 반복 전송이나 재검증이 생깁니다. 파일별 SHA-256을 URL에 포함하고, 해당 주소에 1년 캐시와 `immutable`을 적용했습니다. 내용 변경은 새 URL에 반영하며 서버는 패키지의 해당 파일을 메모리에 유지합니다. 로컬 HTTPS Chrome에서 변경 전후 각각 새 컨텍스트로 5회 비교한 결과, CSS·JavaScript·jQuery 합계의 재방문 전송량은 **22,034B → 0B**, 첫 방문 전송량은 **109,867B → 109,968B**였습니다. HTML이나 업무 API 전송량과 화면 표시 시간은 이 시험의 범위 밖입니다. ## MySQL 포털의 중복 수신

원격 수신의 응답이 유실되면 Java 송신기가 같은 이벤트를 보낼 수 있습니다. 수신 이력 조회 후 INSERT하는 방식은 두 요청 사이에 경쟁 구간이 생깁니다. PHP 수신기는 이벤트 ID를 기본 키로 먼저 기록하고, 수신 이력과 요약을 같은 트랜잭션에서 커밋합니다. 같은 이벤트는 기본 키 레코드 잠금을 기다리며, 중복 키가 발생한 요청은 롤백 후 저장된 내용 해시를 다시 읽습니다. 실제 MySQL 8.4.13에서 세 번 실행해 같은 내용의 두 요청은 모두 **204**, 다른 금액의 재사용은 **409**, 수신 이력과 요약은 **각 한 건**임을 확인했습니다. 관측한 대기 시점에는 시험 도구의 샘플링 지연도 포함됩니다. ## 월마감 실패 후 재시작

결산 저장 실패 뒤 실행 때마다 새 배치 인스턴스를 만들면, 같은 부서·기간의 앞선 실패와 후속 실행을 별도로 연결해야 합니다. Spring Batch에서 부서와 기간을 작업 식별자로 쓰고 같은 인스턴스를 재시작하도록 했습니다. 운영 시 Batch 메타데이터와 마감 상태를 함께 관리해야 하며, 마감 중인 기간은 재시작해 결과를 확정할 때까지 새 신청을 받지 않습니다. 실제 Oracle 시험에서 결산 행 저장 충돌을 만든 뒤 원인을 제거하고 재시작해, **인스턴스 1개에 실패·성공 실행이 각각 1건**, 확정 집행액 **45,000원**임을 확인했습니다. ## 규정 변경과 과거 계산 재현

항상 최신 수식을 읽으면 규정 테이블은 단순하지만 이미 접수된 신청의 근거 금액이 바뀝니다. 신청 시점의 수식과 발행 세대, 평가기 버전을 신청에 고정했습니다. 복구도 새 발행 세대로 기록하므로 과거 규정 사본과 여러 평가기 동작을 계속 보관하고 시험해야 합니다. 실제 Oracle에서 180,000원 학회비의 인정액이 **기존 144,000원, 90% 발행 후 신규 162,000원, 복구 후 신규 144,000원**이었고 이미 우대 규정을 적용한 신청은 162,000원을 유지했습니다. 다른 조직과 병원 일반 교육비의 계산도 함께 대조했습니다. ## 방문자·부서 사이의 증빙 격리

화면에서 링크를 숨기는 방식만으로는 이미 알고 있는 증빙 주소로 들어오는 직접 요청을 제어하기 어렵습니다. 서버가 세션의 현재 업무 공간을 정하고, MyBatis는 공간 ID와 신청번호를 함께 바인딩합니다. 새 목록·다운로드 경로에도 같은 범위를 적용하고 시험해야 하며 SQL 조건과 합성 부서별 데이터 관리가 추가됩니다. 공개 Chrome에서 증빙 주소로 직접 요청했을 때 다른 방문자와 같은 방문자의 다른 부서는 모두 **404**를 받았습니다. 시연용 역할은 세션에서 전환하며 실제 조직의 SSO나 실물 증빙 파일 권한은 시연 범위 밖입니다.
