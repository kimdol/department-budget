# 공개 체험 보관과 직원 업무 도우미

## 보관 기준

첫 화면 **체험 설정** 제목 바로 아래에 보관 기간을 표시합니다. 시작한 뒤에도 같은 위치에서 확인할 수 있습니다. 새 방문자에게 생성한 기본·보조 부서를 한 쌍으로 관리합니다. 서버가 해당 세션의 화면 또는 업무 API 요청을 받으면 기본 부서의 마지막 이용 시각을 갱신합니다. 공개 업무 공간에는 30일을 적용합니다. 10일로 줄이면 일찍 지워지는 만큼 이력 확인 기간도 짧아집니다. 현재 규모에서는 30일을 유지합니다.

V025에는 마지막 이용 시각이 없습니다. V026 적용 시 기존 공간에도 적용 시각을 부여해 과거 신청일로 유휴 기간을 추정하는 일을 피합니다. 보관 기간이 지났고 양쪽 부서에 미전송 이벤트와 진행 중 월마감이 없어야 후보가 됩니다. 한국 시간 03:15에 한 번 실행합니다. 기본 부서 행을 잠근 뒤 조건을 다시 읽으므로 목록을 추출한 직후에 방문한 공간은 보존됩니다. 웹 프로세스가 실행 중일 때 동작하며 중지 시간에 놓친 분량은 다음 실행에서 다시 검사합니다.

삭제는 한 방문자씩 커밋합니다. 신청·증빙·원장·규정·배정·결산과 해당 공간의 월마감 배치 이력을 함께 지웁니다. 전송한 포털 이벤트 ID와 부서 ID는 같은 트랜잭션에서 정리 대기표에 보관합니다. 별도 제한 계정으로 MySQL 수신 이력과 요약을 삭제하고 커밋한 후 대기표를 비웁니다. 포털 작업이 실패하면 해당 식별자가 남아 재시도할 수 있습니다. 다른 방문자와 브라우저 개인 장부는 대상에서 제외합니다. [만료 판정과 원장 정리](../src/main/java/kr/budget/retention/DemoRetention.java) · [MySQL 재처리](../src/main/java/kr/budget/retention/PortalCleanup.java)

## 운영 점검

- [Oracle 읽기 전용 집계](../ops/DemoInventory.java)는 앱 스키마 할당 바이트, DATA 할당 한도, 부서·신청·미전송 건수와 후보 쌍 수를 표시합니다. 삭제 직후에도 할당된 세그먼트의 빈 공간은 이후 INSERT에서 재사용할 수 있어 할당 바이트가 바로 줄지 않을 수 있습니다.
- 적용 전 Oracle은 앱 스키마 **7,340,032바이트(7MiB)**, DATA 사용자 할당 한도 **536,870,912바이트(512MiB)**, 부서 542개·방문자 271쌍·신청 675건·미전송 0건이었습니다. 전체 DATA 사용량 조회는 앱 계정에 권한이 없었습니다. 마지막 활동 기록이 없어 이 시점의 만료 건수는 산출할 수 없었습니다.
- 같은 시점에 MySQL 수신 계정에서 볼 수 있는 표의 데이터·인덱스 통계 합계는 **98,304바이트**, 이벤트 수신 이력 257건, 신청 요약 179건이었습니다. [읽기 전용 집계와 전용 계정 설정](../ops/portal_cleanup_account.py)
- 서버에서 Oracle 도구는 서비스의 기존 JDBC 환경을 사용합니다. MySQL 도구는 포털 서비스 환경으로 `--inventory`를 주면 읽기만 합니다. 전용 계정 초기 설정은 운영자가 같은 환경에서 옵션 없이 실행하고 MySQL 관리 암호를 대화식으로 입력합니다. 전용 계정은 접속 VM 호스트에서 TLS를 사용하며 두 수신 테이블의 삭제와 키 열 조회만 허용합니다. 설정 파일은 root와 서비스 그룹만 읽을 수 있습니다.
- `BUDGET_CLEANUP_ENABLED=true`인 웹 서비스가 일일 정리를 실행합니다. 운영 로그의 삭제한 쌍 수와 포털 대기 수를 확인합니다. Oracle 대기 건수는 `select count(*) from demo_portal_cleanup`으로 조회합니다.

## 배포 검증과 포털 권한

공개 배포 직전 새 기준으로 삭제 후보는 **0쌍**이었고 V026 적용 전후 부서·신청 건수는 같았습니다. 공개 Chrome에서 기존 신청함의 세 화면 폭, 지연 로딩, 도우미를 포함한 5건이 통과했습니다. 로컬 MySQL에서는 전용 권한으로 만료 공간의 수신·요약을 삭제하고 다른 방문자의 두 기록을 보존했습니다. `python ops/test_portal.py --retention`으로 재현합니다. [배포·용량 기록](measurements/deployment-retention.json) · [실제 Oracle 시험](https://github.com/kimdol/department-budget/actions/runs/44927202859)

2026년 11월 22일 03:15:01(한국 시간) 운영 로그에 삭제된 방문자 0쌍, 정리를 기다리는 포털 공간 0개가 기록됐습니다. 이 실행에서 MySQL 삭제 권한을 사용할 기회는 없었습니다. VM에서 최근 실행 결과는 다음 명령으로 확인합니다.

```sh
sudo journalctl -u department-budget --grep='Demo cleanup removed' -n 1 -o cat
```

같은 날 전용 계정의 첫 설정 이후 VM이 재부팅됐습니다. 비공개 설정 파일은 남았지만 저장된 자격 증명으로 접속하면 MySQL 오류 1045가 발생했습니다. 종전 설정 도구는 파일이 있으면 종료해 재실행할 수 없었습니다. 수정한 도구는 MySQL에서 계정 생성 여부를 확인합니다. 이미 존재하는 계정은 저장된 자격 증명으로 접속해 신원을 확인한 뒤 필요한 권한만 다시 부여합니다. 오류 메시지는 처리 단계와 오류 코드만 출력합니다.

설정을 재개한 뒤 웹 서비스의 OS 계정으로 MySQL에 접속했습니다. TLS 1.3을 사용했고, 두 표의 삭제와 식별 열 조회 권한을 확인했습니다. 각 표에 `WHERE 1=0`과 식별 열 조건을 적용해 DELETE를 실행한 뒤 ROLLBACK했습니다. 변경된 행은 양쪽 모두 0건이었습니다. 만료 방문자의 실제 운영 데이터 삭제는 만료 대상이 생기는 날 실행됩니다.

관리자가 VM에 접속한 뒤 아래 명령을 실행하면 전용 계정에 필요한 권한을 설정합니다. MySQL 관리 암호는 해당 터미널 입력창에서만 사용합니다.

```sh
sudo systemd-run --pty --wait --collect \
  -p EnvironmentFile=/etc/department-budget/portal.env \
  /usr/bin/python3 /opt/department-budget/tools/portal_cleanup_account.py
```

## 직원 업무 도우미

**내 신청함 시작 → 내 신청함 → 대화형 업무 도우미**로 엽니다. 현재 선택한 신청을 대상으로 합니다. “가용 예산 알려줘”, “신청 상태 알려줘”는 현재 화면에서 금액과 상태를 읽어 줍니다. “영수증 첨부해줘”는 보완 요청의 신청명과 금액을 먼저 표시합니다. **이 영수증 첨부**를 누르면 실비와 확인 차수로 합성 영수증을 첨부합니다. “다시 제출해줘”는 일치하는 영수증을 확인한 뒤 별도의 **이 신청 재제출** 확인을 받습니다. 직원에게 결재 권한이 필요한 요청이 들어오면 담당 역할을 안내합니다.

현재 해석기는 정해진 한국어 표현을 인식합니다. 입력 문장과 대화 내용은 브라우저 컴포넌트에서만 다룹니다. 향후 로컬 모델은 `IntentInterpreter`를 구현해 등록된 의도 하나만 제안할 수 있습니다. 화면이 신청을 선택하고 사용자가 변경 내용을 확인하며, 기존 Spring API가 세션 역할·부서·신청 상태·차수를 검증합니다. 모델에 세션 토큰이나 임의 API 호출 기능을 전달할 필요가 없습니다.
